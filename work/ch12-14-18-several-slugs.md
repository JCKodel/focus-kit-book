# ch12-14-18-several-slugs

**Objective.** After chapters 12, 13, 14, 16, 18 and 19 the reader can type `/propose` or `/apply` with several slugs and say what happens: one subagent per slug, a fresh session running the command on its own line, opened at once where the tokens and `after` let the lines run and the rest reported, in the one folder on trunk or each in its slug's worktree with a worktree per delivery; the session edits nothing and relays each subagent's question to the person; the commands keep `disable-model-invocation`, because the person's command names every slug; and the command may say to decide alone or to build as well, the page recording both.

**Behaviour.** What the reader can do or explain afterwards:

* Asked "what does `/propose search-catalog renew-loan` do?", answer from chapter 12: the session opens one subagent per slug, each a fresh session with only its opening message and the project's files, running `/propose` on its own slug as if typed alone; the session itself edits nothing.
* Say where the subagents work: on trunk, all in the folder where the session runs, each changing only its own line and page, and, for `/apply`, each staging only its delivery in the folder's one index (chapters 13 and 18); with a worktree per delivery, each in its slug's worktree, `/propose`'s creating it and writing there from `main/` as a `/propose` typed alone does, `/apply`'s sent to its path and working with every file and command there (chapters 12, 13 and 18).
* Using chapter 14's four-line block, say which subagents open: `/propose search-catalog renew-loan` opens both at once, both tokens starting with `P`; with both pages `[>]` and `lend-book` still `[*]`, `/apply search-catalog renew-loan` builds `search-catalog` and reports that `renew-loan` waits, without waiting for it.
* Say what happens to a question: the subagent reports it with what the person needs to answer and stops; the session asks the person and sends the answer back, to that subagent where the host can resume it, else to a new one opened on the slug, which resumes the line's `[~]` on the command's word.
* Say why the flag stays: the person's command names every slug, and each subagent takes its slug from the message that opens it and runs on that word, so nothing needs the flag lifted; lifting it would bring back a message that only mentions a command running it (chapter 8) and an agent going on into `/propose` instead of stopping at the queue line (chapter 11).
* Say what "decide alone" records: each question answered by the subagent's own recommendation and written on the page as the agent's answer, so the reading finds it; chapter 19's batch is that command, not a session per line told in conversation.
* Say what "build as well" records and costs: a new subagent runs `/apply` when a page reaches `[>]`, the page says it was built before the person read it, the person reads the pages and diffs at the end and still decides each commit, one delivery at a time; a hole the page would have shown in one turn costs, found in the diff, another `/apply`.
* Say why chapter 16's governor still holds: a command's subagent is not specialized; it runs the whole command on its line, so each delivery still has one agent that reads, plans and builds.
* Edge, refusal: an `/apply` subagent not sent to the delivery's worktree's path refuses as a session opened elsewhere does, edits nothing and gives the path (chapter 13).
* Edge, one slug: `/propose lend-book` and `/apply lend-book` read as before; no sentence implies a single slug opens a subagent.
* Edge: no passage names a version, a date, a run, the kit change that brought the rule, the changelog's incident or `skip-worktree`; nothing implies Case B ran on the process.
