# testing-and-agents

**Objective.** After chapter 16 the reader can say which test guards each FOCUS piece and what it swaps, follow one rule of the clinic through a test at every level, the client orchestrator's test with its fakes included, and say, with the clinic's own record, how a slice and its tests keep an agent's reading small and tell it when it is done.

This page replaces the one of the first `/apply` (at `c54d011`), after `clinic-orchestrator-tests` gave the client orchestrators their tests and `four-pieces-injection` moved chapter 15 to `book-v1/four-pieces` (`e6653b5`). The draft `book/*/16-testing-and-agents.md` is the base; what that `/apply` learned is kept below where it still holds.

**Behaviour.**

* The reader can name, for each piece, the test that guards it in the clinic and what that test swaps: a use case gets its data and `now` and swaps nothing; a repository runs against an in-memory SQLite with the real migrations; the server orchestrator is driven through `app.request` with that database and a fake clock; the client orchestrator's event functions get fake repositories and `now`; the phone's storage (`remembered.ts`) gets a fake `localStorage`; the network is guarded through the shared `request`, tested with a fake `fetch`; the view and the hook are driven in a browser by Playwright.
* The reader can follow the 24-hour cancellation rule through five tests, the use case, the repository, the route, the client's event function and the screen, and say what each asserts that the others do not.
* The reader can say why the route's test fakes the clock and the other unit tests pass `now` as data: the route and the hook are the only code that reads `new Date()`, and each hands it on (chapter 15's "one event, one new state" as one test, as chapter 15 promised).
* The reader can say what a fake is for, from the clinic's event test: the event function receives its repositories, the test passes a second implementation that answers what the test sets, and asserts which repository was called, with what, and the new state; a repository the test does not expect fails if called.
* The reader can say, from the clinic's run record, how many files of `src/` the agent read to build a delivery inside the appointments slice, how many of them were in that slice, what it read to start a new slice (a sibling slice as its model), and that it ran the slice's tests alone before the whole verify (chapter 14's promise that the slice bounds what an agent reads).

**Out of scope.**

* Any change to the clinic, a test for `api.ts` or the hooks included: the end-to-end tests drive them, and a new tag costs more than it teaches.
* A new agent run, or counting the `orchestrator-tests` run in section 6: it touched all eight slices, so it does not show one slice's bound.
* How the event functions were built (the recorded run): chapter 15 chose not to tell it.
* Coverage percentages, test-first as a doctrine, the testing pyramid as theory: the chapter shows the clinic's levels and what each proves.
* Mock libraries, module mocks and dependency-injection frameworks: the clinic passes its fakes.
* Every other rule and slice: one rule through every level carries the idea; exercise 16.1 takes a second.
* Chapter 6's "only the orchestrator has injected dependencies, and they are the repositories" (found by `four-pieces-injection`): a candidate line of its own.
* Parallel agents: Part IV.
* The queue listing of chapter 9, which shows this line as `[ ]`: a snapshot of that day.
