# pages-and-release

**Objective.** The author pushes to `main` and the site at <https://jckodel.github.io/focus-kit-book/> shows that commit. The author pushes a `v*` tag and a GitHub Release appears with the PDF and the EPUB of both editions. Neither happens when `make verify` is red.

**Behaviour.**

* A push to any branch runs `verify` as today. Nothing is published from a branch other than `main`.
* A push to `main` runs `verify`, then `pages`. `pages` builds the site with `make build` and deploys it to GitHub Pages. When `verify` fails, `pages` does not run and the site keeps the previous version.
* Two pushes to `main` in quick succession never deploy out of order: a new `pages` run waits for the running one, and a queued run that is now stale is dropped.
* A push of a tag matching `v*` runs `verify`, then `release`. `release` runs `make book` and creates a GitHub Release named after the tag, with the four files of `output/` attached under their exact names and notes generated by GitHub. When `verify` or `make book` fails, no Release is created.
* A tag with a `-` in it (`v0.0.1-test`, `v1.0.0-rc1`) creates a pre-release. Any other `v*` tag creates a published Release, which becomes the latest one.
* Because the file names never change, `https://github.com/JCKodel/focus-kit-book/releases/latest/download/<file>` always points to the newest published Release.
* The Release files match what `make book` produces locally: pandoc and WeasyPrint in Actions run the same versions as the local build the `pdf-epub` delivery proved (pandoc 3.11, WeasyPrint 69.0).
* A draft chapter goes into the Release with its banner, as `make book` already does. Drafts are removed by the chapters' own deliveries, not by this one.
* The agent never pushes, tags or releases (docs/05 §5). Everything this delivery publishes waits for the author's push.

**Contract.**

Files:

```
.github/workflows/verify.yml   three jobs: verify (unchanged), pages, release
docs/01-Architecture.md        stack row Automation, the tree line of verify.yml, the Environments table
README.md, README.pt.md        only if a sentence about Pages or Releases becomes wrong; no new links
docs/06-Queue.md               pages-and-release [x]
```

`verify.yml`:

* `on: push` stays as it is, with no filter: it already fires for every branch and every tag.
* Top-level `permissions: contents: read` stays. Each job that publishes raises its own permissions and nothing else.
* Job `verify`: unchanged.
* Job `pages`:
  * `needs: verify`; `if: github.ref == 'refs/heads/main'`.
  * `permissions: pages: write, id-token: write, contents: read`.
  * `environment: github-pages`, with its `url` set from the deploy step's `page_url`.
  * `concurrency: group: pages, cancel-in-progress: false`.
  * Steps: checkout, setup-python, `make build` (strict, into `site/`), `actions/configure-pages`, `actions/upload-pages-artifact` with `path: site`, `actions/deploy-pages`.
* Job `release`:
  * `needs: verify`; `if: startsWith(github.ref, 'refs/tags/v')`.
  * `permissions: contents: write`.
  * Steps: checkout, setup-python, install pandoc 3.11 from the `.deb` of pandoc's GitHub release for amd64, install WeasyPrint 69.0 with pip (plus whatever system libraries it needs on `ubuntu-latest`, found by /apply), `make book`, then `gh release create "$GITHUB_REF_NAME" output/*.pdf output/*.epub --verify-tag --generate-notes --title "$GITHUB_REF_NAME"`, with `--prerelease` added by `case "$GITHUB_REF_NAME" in *-*) ...; esac`. `GH_TOKEN` is `github.token`.
  * The system libraries WeasyPrint needed on the runner are recorded in "What happened".
* Actions are pinned by major version (`@v4`, `@v5`), as `verify` already does.

Release assets, exact names, from the `pdf-epub` contract:

```
one-page-at-a-time.pdf        one-page-at-a-time.epub
uma-pagina-de-cada-vez.pdf    uma-pagina-de-cada-vez.epub
```

Setup the author does once, before the first push (written here and in the commit body, never done by the agent):

* Settings, Pages, Source: "GitHub Actions" (or `gh api -X POST repos/JCKodel/focus-kit-book/pages -f build_type=workflow`).

**Out of scope.**

* Uploading to books.kodel.com.br: the author does it by hand (ADR-0014).
* Links to `releases/latest/download/...` in the READMEs or the site: the link check would fail until the first published Release exists. They belong to `launch`.
* A custom domain for the site: nobody has asked for one.
* Running `make book` on pushes that are not tags: `make book` is not part of `make verify` (docs/01), and nothing has broken it between tags.
* Versioned site builds (mike): the site follows `main`, and only the files have versions (ADR-0014).
* Release notes written by hand, or a changelog: the tag message and GitHub's notes are enough until `launch` says otherwise.
* Pinning actions by commit SHA: `verify` pins by major version, and no supply chain incident has made that a concern yet (docs/05 §7).

**What happened.**

* `actionlint` 1.7.12, built with `go install` into a scratch folder outside the repository, reports nothing. shellcheck is not installed here, so actionlint did not lint the `run:` scripts; the `release` script avoids an unquoted variable anyway: `--prerelease` goes through `set --` and `"$@"`, checked by hand for `v1.0.0` (none), `v0.0.1-test` and `v1.0.0-rc1` (both `--prerelease`).
* No container runtime on this machine (no docker, podman or colima), so the `release` install steps were read against the sources instead: the pandoc `.deb` URL `https://github.com/jgm/pandoc/releases/download/3.11/pandoc-3.11-1-amd64.deb` answers 200, and WeasyPrint 69.0's `docs/first_steps.rst`, "Ubuntu >= 20.04", lists for a pip install from wheels: `libpango-1.0-0 libharfbuzz0b libpangoft2-1.0-0 libharfbuzz-subset0`. Those four are the system libraries the step installs. The first `release` run on a tag is the real proof (Author item below).
* `apt-get update` runs before the `.deb` install, not only before the WeasyPrint libraries, so both installs see a fresh package index.
* `make book` locally still writes the four files; `make verify` green; `output/` and `site/` stay ignored.
* READMEs checked: they link to the Releases page, which stays right; no change.
* docs/01: Automation row, the tree line of `verify.yml` and the Pages and Release rows of the Environments table now name the jobs and their order. No new term, rule or ADR: ADR-0014 already holds the decision.
* Nothing diverged from the contract.
