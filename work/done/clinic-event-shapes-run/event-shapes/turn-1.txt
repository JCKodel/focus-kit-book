**How I read the slug.** `event-shapes` isn't in the queue. The closest thing is a line in the Out of scope section of `work/done/update-type.md`: "docs/01 naming every event shape (sync, async, `Update | Promise<Update>`, `{ update, report }`, `BookingOutcome`): another delivery." So I read it as: docs/01 names every shape an event function can answer, so the next events file picks one from the list instead of inventing another.

**What's in the code today.** Eight events files use these shapes:

1. A plain event, `(state, ...inputs) => State`, such as `typeName` and `pickDay`. Some take no state: `open()` and `close()` in cancel.
2. A starter that returns a whole `State` (9 of them), such as `addStarted` and `loadSlotsStarted`.
3. A starter that returns `Started<S>`: `submitStarted` in booking and `saveStarted` in weekly hours.
4. An async event that returns `Promise<Update<S>>`, the common case.
5. `Promise<BookingOutcome>`: an update, or the next event to run (`BookingNext`).
6. `Promise<WeeklyHoursAnswer>`: `{ update, report? }`, where the report goes to the professionals section.
7. `hoursReported`, which returns `Update | Promise<Update>`.
8. Readers that aren't events: `daysOf`, `tooLateToCancel`, `retryOf`, `linesOf`.

**One thing I found.** docs/01 says "the in-flight state is published the same way, as an update of the current state". Three hooks don't do that:

- `useOwner` publishes `setState(submitSignInStarted())` and `setState(submitSignOutStarted(email))`, a whole state.
- `useCancel` publishes `setState(openEvent())`, also a whole state.
- `useCancel` also sends `state.phone` and `state.code` taken from the render, not from the state that was checked.

This is the same class of bug that `booking-submit` and `hours-save` fixed. It can lose a keystroke typed just before submitting.
