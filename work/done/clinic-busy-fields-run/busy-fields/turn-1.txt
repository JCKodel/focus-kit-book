I have enough to see the shape of this; before I write anything I need you to confirm what it means, because `busy-fields` isn't in docs/06 and no document defines it.

**What I see.** Every form in the app disables its **buttons** while a request is in flight, but none disables its **fields**. That covers 10 inputs in 5 views:

| View | Fields that stay editable while busy |
|---|---|
| Booking form (client) | Name, Phone |
| Cancel with a booking code (client) | Phone, Booking code |
| Owner sign-in | Email, Password |
| Professionals | Name (add), New name (rename) |
| Weekly hours | every From and To |

`hours-save` listed "Disabling the From and To fields while saving" as out of scope, so I read `busy-fields` as picking that up for the whole app.

The gap is real in the owner screens. A time typed while "Save hours" is in flight is silently lost when the save succeeds and the row closes. The same happens to a name typed during an add or a rename. In the client screens it's milder: what gets booked or cancelled is what was on screen at the tap, not what was typed afterwards. `booking-submit` and `hours-save` made sure a later edit survives a refusal. Disabling the fields means there is no later edit to lose.

The build would be small: `disabled={busy}` on each field, plus one field assertion added to each view's existing "disables … while in flight" Playwright test. No contract change, no event or hook change.

**Questions (my recommendation first in each):**

1. **Scope.** Should every field be disabled whenever the buttons next to it are, in all five views? In the professionals section that means every field of the section, including the hours editor inside it, just as busy already disables every button there. Or did you mean something else by `busy-fields`?
2. **`disabled` or `readOnly`.** I recommend `disabled`:
   - it's the same attribute the buttons already use, so the rule reads the same everywhere;
   - it greys the field out, so the person sees it's locked;
   - the existing tests can check it with `toBeDisabled`.

   The cost: on a phone, sending with the keyboard's Enter closes the keyboard, and after a refusal the person taps the field again. `readOnly` keeps focus and the keyboard but gives no visual cue.
3. **Where it goes in the queue.** I'd add it to Milestone 1.1, after `event-shapes` and before `m1.1-review`, and add a clause to the milestone paragraph so the review checks it. The paragraph gains a clause like "and no field can be edited while a request it belongs to is in flight". The alternative is Milestone 2, but this is cleanup of milestone 1 screens, not "the owner runs the day".
4. **Docs.** Shape 2 in docs/01 says the update exists "so what was typed meanwhile survives". I'd leave the events untouched, since the update still guards against edits between render and publish. Should the page also change that sentence to say fields are locked while busy? My recommendation is to leave the sentence as it is and record the new rule under States in each view's section of the page instead.
