# four-pieces

**Objective.** After chapter 15 the reader can place every file of a feature in one of the four pieces, view, orchestrator, use case and repository, on the client and on the server, follow one event through them to a new state, and decide for a feature which pieces pay their way and which it does without.

**Behaviour.**

* The reader can say what each piece does and what it may not do, from the clinic's table, and name the file that plays each piece in a slice of the clinic.
* The reader can say why a clinic slice has two orchestrators and two repositories (the hook and the route; `api.ts`, `remembered.ts` and `repository.server.ts`) and one set of use cases that both sides import: the server enforces a rule, the client uses the same function only to decide what to show.
* The reader can follow a booking from the tap on "Book" to the screen showing the booking code, naming at each step the piece, the file and what it hands on, and can say where the flow would have gone back the wrong way (the view changing state, a use case calling a repository).
* The reader can say what the clinic's orchestrators receive in place of injected repositories (the route receives the database and passes it to the repository functions; the hook imports its repositories) and why the clinic chose that: tests swap only the database, so repository objects would be ceremony.
* The reader can take a feature and say which pieces it needs: a use case only when there is a rule, a repository only when there is I/O, an orchestrator when an event leads to a new state, a view when there is a screen; and can say when FOCUS whole costs more than it gives (the brownfield project of chapter 8 chose neither) and when the two principles alone are the answer.

  5. What the clinic injects. `appointmentsRoute(db)`: the route receives the database, the driver, and passes it to each repository function; the clinic's docs/01 bullet quoted whole: "Server routes that need the database are functions of it (`clinicRoute(db)`), so Vitest drives them through Hono's `app.request` against an in-memory SQLite (`testDatabase.server.ts`)." The hook injects nothing: it imports `api.ts` and `remembered.ts`. Said as the clinic's choice against ADR-0016's "the orchestrator is the only piece with injected dependencies, and those are the repositories": in a language of functions, the one swap tests need is the database, and a repository object passed in would be a piece for ceremony (KISS). Chapter 16 shows the tests.
  6. When the pieces pay their way. A piece exists when it has a job: a use case when there is a rule (`health`, chapter 14, pointed to), a repository when there is I/O, an orchestrator when an event leads to a new state, a view when there is a screen. The cost, from the clinic's ADR-0002 §Consequences, quoted: "A slice has more files than a component that fetches on its own; a file appears only when it pays its way." Where it pays: rules that must each have a test (the clinic's product value, the same ADR's Context). Where it does not: the brownfield project in chapter 8, where FOCUS whole meant a large refactor and the answer was neither; the two principles alone, chapter 14, as the middle answer. KISS, YAGNI and DRY decide, as chapter 6 said, pointed to.
  7. Key points, at most five, one of them: a piece is written when it has a job, and the "Forbids" column keeps it to that job.
