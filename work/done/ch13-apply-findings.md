**Objective.** After chapter 13 the reader can say what `/apply` does with a flaw: one in what its delivery built or changed is fixed in that delivery, with a test, a case the page did not name included; one it cannot fix without widening the page or without a decision no document answers is a note with what the person may do, or, when grave or leaving a Done when item unticked, a `[?]` for the person's answer; one in anything else is a note, a line only when grave; and can read the mark that opens its last message, `🚨`, `⚠️` or `✅`, say which tests it writes and no others, how long verify may take, and which slow tests it runs before it ends.

**Behaviour.** What the reader can do or explain afterwards:

* Say why a flaw in what the delivery built is fixed in it: the page is the scope, and fixing what the delivery built is not widening it; a fault the review finds in the text the delivery wrote, a case the page did not name included, is fixed in the session, with a test for the fix, and verify runs again.
* Say what happens to a flaw in what it built that it cannot fix without widening the page or without a decision no document answers: it is not fixed and not guessed; it is a note on the page with what the person may do; when it is grave, or leaves a Done when item unticked, the line waits as `[?]` for the person's answer instead.
* Say what happens to a flaw in anything the delivery did not build or change, one older than the delivery in a file it edits included: it is a finding; a grave one, by chapter 11's three tests, becomes a `[ ]` line ending `· from <slug>`, the delivery that found it (chapter 14 says where it goes); every other finding, and one nobody can say is grave, is a note on the page under `## For the review` (chapter 14 shows the note; chapter 15, the review that copies it).
* Explain the error the rule prevents: in one project, on 2026-11-12, 32 of the 130 lines of its first milestone had come from a finding, 22 of them from a delivery review; twenty-four in a row were findings or the design line of one, most about one screen and several a flaw in what the delivery before had just built, each with its own page, proof and review, which found the next, seven generations deep, all above the line that answers the milestone's first clause.
* Read the last message's first lines: `🚨` before each new line and each flaw that blocked the delivery, `⚠️` before each note and a verify over its ceiling, `✅` when the delivery is done and left none; a blocked `/apply` opens the same way. Edge: a delivery that left one note opens with `⚠️`, never `✅`. Why: in the project above each command named the lines it added in a last message shaped like every other, and the person saw the drift only after the twenty-four.
* Say which tests `/apply` writes: those docs/04 asks for what the page says and for each flaw it fixes, and no others; a test too slow for verify goes with the slow tests, and `/apply` says so.
* Say verify's ceiling: five minutes unless the person says otherwise; `/apply` says how long verify took, and over the ceiling that is a note for the review, which says which tests go to the slow ones. Why: suites grow until verify delays every delivery.
* Say which slow tests run when: the Verify slot lists them one line each, the command and what it covers; `/apply` runs those that cover what its delivery changed, and only those, before the delivery ends; the milestone review runs them all. Why: a slow test run only at the review finds a break far from the delivery that made it, so a team keeps it inside verify to be safe and every delivery pays for it.
* Follow the `lend-book` example: the first candidate, `insertLoan` turning every failure into `AlreadyLent`, is fixed with a test that a failure other than the unique index stays `DatabaseFailed`; the second, the suspended member not told until when, is in what it built but needs a decision no document answers, so it is a note under `## For the review` with what you may do, and the last message opens with `⚠️` before that note; the queue tree that follows is unchanged.
* In the person's review, check each fix has its test and no test the page did not ask for, how long verify took, and that each candidate was fixed, written as a note, or, when grave, a line ending `· from <slug>`.
* Find all of this in chapter 13 in both editions, in the Portuguese one with docs/03's terms (achado, achado grave, nota, testes lentos), `## For the review` and `· from` kept as the kit writes them.
