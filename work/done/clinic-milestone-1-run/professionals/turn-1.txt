Before I write, I need your answer on four things. Each one starts with my recommendation:

1. **Duplicate names: refuse them.** I'd refuse a name that an active professional already has, ignoring case (new code `ProfessionalNameTaken`). The client picks a professional by name, so two "Ana Costa" entries would be impossible to tell apart. A removed professional's name can be used again. The alternative is to allow duplicates and leave it to the owner.

2. **Who can read the list: one public route, `GET /api/professionals`.** It returns the active professionals in alphabetical order. The alternative is an owner-only route now and a second public route in `book-appointment`.

3. **Remove asks for confirmation on the same row.** Tapping "Remove" turns the row into "Remove Ana Costa? Clients will no longer see them." with "Remove" and "Keep" buttons. This matters because removal can't be undone. The alternative is the browser's `confirm()` dialog, which is simpler but looks rough on a phone.

4. **Store the removal time, not a yes/no flag.** The column would be `removed_at` (a UTC instant, empty while the professional is active) rather than `removed 0/1`. It costs the same and records when it happened. This is the one choice that's expensive to change later, because it's a column.
