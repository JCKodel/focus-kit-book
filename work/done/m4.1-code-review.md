# m4.1-code-review

**Objective.** After this delivery the author knows what the clinic's code that M4.1 changed still owes, as findings each decided, with every confirmed finding a line in M4.2; the review is recorded so that chapter 23 can tell it, and docs/05 §8's code-review recipe says where a range ends when the milestone's last change to the guided project has no chapter tag, what to do with a kit update inside it, and that findings one change settles may share one line.

**Behaviour.**

* `/code-review high` reviews the five clinic runs of M4.1, `a3e2470...6edc9ad`, headless, from the clinic's root. The kit update `a3e2470` just after `book-v1/four-pieces` is left out by starting the range on it. The review edits nothing.
* The /apply session checks each finding against the clinic's code and documents and gives its assessment. The author decides each one, confirmed or rejected, with a one-sentence reason. Nothing is fixed.
* A confirmed finding that an existing M4.2 line already covers adds no line. That line gains words only if the finding adds something, and the record says "already queued".
* A confirmed finding that an open line of the clinic's own queue covers (milestone 1.1's `route-errors` and `minutes-of` may overlap) still becomes an M4.2 line, which names the clinic's line and what the finding adds. The clinic's docs/06 is never touched.
* The review's own session writes each confirmed finding as a `[ ]` line in the book's M4.2, just before `m4.2-review`, and adds one clause about the clinic's code to M4.2's paragraph. It stages the book's docs/06. Nothing in the clinic changes.
* docs/05 §8's code-review recipe covers a range whose end has no chapter tag, a kit update inside it (step 1), and findings that share one line (step 5), so `m4.2-code-review` or `m5-code-review` follows it without reopening this page.
* The whole run is recorded, so chapter 23 can tell it and quote it.
